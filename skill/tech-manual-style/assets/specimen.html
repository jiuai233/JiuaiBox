5.3

The effect sandwich

Commit what you are about to do, do it, then commit what happened; a crash in the middle leaves a clear question, not a silent gap.

The log can commit its own records atomically, but it cannot make a card charge atomic with them. If the process dies right after the charge, did the customer pay? After this section you can split any outside action into phases so every crash point has a defined, safe recovery.

Why effects need their own phase

An effect is anything that changes the world outside storage. Effects may not run inside a commit spec §1, invariant 4. A commit holds the write queue, so waiting on the network would stall every other writer (the commit (p. 29)).

Core rule

“A session atomically commits immutable entries and full job records. Only committed state is observable.”

a two-phase payment job test/examples/12-jobs.tsTS
$ node test/examples/12-jobs.ts

log: [ 'job.prepare', 'job.charge', 'job.terminal' ]

Commit the intent, perform the effect, commit the outcome; a crash in the middle reruns only the effect phase. The phases of spec §5.1's payment example.

What this means for you
  • Create the key in the intent phase. A key created inside the effect phase changes on every rerun.
  • Commit the outcome and its consequences together.
  • Guard a second effect in the same phase with a memo.
